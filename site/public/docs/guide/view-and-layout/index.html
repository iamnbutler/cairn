Building an app · Chapter 3

The view and layout

What an app shows, as a tree of boxes and text that Lean lays out in whole points.

An app's view is a pure function from its state to a tree of nodes. Lean lays the tree out, hit tests it, and turns it into the frame the host paints. Because all of that is Lean, "Reset's button is on screen" and "a click at its centre presses it" are theorems about the code that actually runs, not about a model of it.

The view function

A window's view takes the app's state and the UI state: the window's size, which control the pointer is over, which is pressed, which has keyboard focus. The runtime keeps the UI state; the view only reads it, for hover colours and focus rings. Counter's button:

A node that performs a move carries a control: the ref of the claim it performs, an accessibility role and a label. Controls are how presence theorems, hit testing and the accessibility mirror find a move on screen. The host gives each control's accessibility element the identifier ^N.

Nodes

There are four kinds of node: a box, a line of text, wrapped text, and a text field.

A box has a style: how it lays out its children, how big it is, and how it is painted.

Layout

Layout is a small subset of flexbox, and everything is in integer logical points, origin at the top left, y down. There are no floats anywhere a theorem looks.

  • A row lays its children out left to right, a column top to bottom, and a stack places them all in the same box, later ones on top.
  • On each axis a node is fixed n, hug (its content's size) or fill. fill children share what is left over equally, to the point: the shares add up exactly, and differ by at most one.
  • Nothing shrinks. When children don't fit, fill children get nothing and the rest overflow. A box with clip cuts its children to its rect.
  • There is no scrolling yet.

Text comes from the host's measurements: Lean asks Core Text how wide a string is in a given font, and lays it out with the answer. That the measurement matches what is painted is an assumption, checked by fuzzing; every layout theorem holds for whatever valid measurements the host returns.

Rigid views

Counter's buttons clip their labels and are fixed in size. That makes the view rigid: no rect depends on the width of a string. For a rigid view, Cairn can prove every control is pressable in every state, with any text measurements, in any window above a minimum size. The next chapter does exactly that. A view whose layout depends on its text can still be checked, one concrete layout at a time.

Surfaces

An app shows a fixed list of surfaces: at most one window, overlay panels that never take focus or clicks, and menu bar items with native menus built from Lean. Each is identified by a place claim. Yap uses all three kinds; Counter has just its window.

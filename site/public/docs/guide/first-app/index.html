Building an app · Chapter 1

Your first app

What a Cairn app is made of, how to run one, and how to start your own.

The pieces

A Cairn app has two halves.

  • Lean holds everything that has meaning: the app's state, the moves a person can make, the view, the claims and their proofs. All of it is pure functions: no IO, no floating point in anything a theorem talks about.
  • Swift is the host. It owns the window, turns mouse and keyboard input into events, runs the effects Lean asks for (write a file, play a sound), mirrors the frame to accessibility, and paints with Metal. It has no application logic.

Between them, two byte buffers cross on every step: a batch of events going in, and a frame coming out. The host protocol describes them.

What you need

  • A Mac on macOS 27 with Xcode, for Swift 6 and the Metal toolchain.
  • Lean 4 through elan. The repository pins the version in lean/lean-toolchain.
  • bun, for the tools that build maps and these docs.
  • The Cairn repository. It isn't public yet.

make build builds the Lean libraries and the Swift host. make demo DEMO=CairnCounter opens Counter in a window. The first build in a fresh checkout takes a while; later ones are incremental.

An app in its own repository

An app lives in a repository of its own and depends on a tagged release of Cairn, the way Yap does. One tag pins both halves: the Lean package and the Swift libraries. Start one with the cairn tool.

cairn new hello makes hello/ with a cairn.toml, an empty claims.lock, and a lean/ whose lakefile sets the claim scope to hello, so the app's ids are hello^1, hello^2, and so on. It also writes a Package.swift for the host. cairn new hello --lib makes a library instead, with no host.

cairn add cairn points the lakefile and cairn.toml at Cairn's latest release in the registry and prints the line for Package.swift. An app can also require Cairn from git at a tag, as Yap's lakefile does:

An app beside the examples

To work on Cairn itself, or to try something quickly without a package, add an app to the Cairn repository beside the examples. It goes in five places:

  1. The Lean module, lean/Examples/<App>.lean, written like Counter: a module that public imports the runtime and only meta imports the claim commands, so the commands stay out of the binary. Add an import of it to lean/Examples.lean, so the ledger and the axiom audit see its claims.
  2. Its exports, cairn_app_init, cairn_app_step and cairn_app_frame, as in Counter's Abi module above.
  3. A library of its own in lean/lakefile.lean. Each app gets one, because every app exports the same three symbols:
  1. The Makefile's app list, which copies each app's library where the host links it:
  1. A Swift executable in host/Package.swift, linking that library, and its main.swift as above:

Then give your claims ids nobody has used (look in claims.lock), build with make build, record the new ids with cd lean && lake exe ledger update, and commit claims.lock with the app. Run it with make demo DEMO=Cairn<App>.

Pick ids in a range of their own: the examples use ^1–^7 (Counter), ^101–^109 (Basics), ^201–^224 (TodoMVC), ^401–^409 (Clock) and ^450 onwards (Tray); the trusted base uses ^900 and up, and ^301–^399 moved with Yap to its own package. Ids are scoped per package: these are all cairn^N. An app in its own repository has its own scope (yap^301), so it can number from ^1.

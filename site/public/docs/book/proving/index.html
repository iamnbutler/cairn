Proving a claim

The proofs an app needs, from a move's one-liner to "Reset is on screen exactly when the count is above zero".

A claim's evidence comes at several strengths. The strongest is a proof that Lean's kernel has checked, using only the three standard axioms. This chapter shows the proofs a small app has, in the order you meet them.

The proof a move needs

A move's sound clause proves that its handler meets its post, for every state (and every key and text operation) where the move is enabled. For Increment, apply adds one and post says the count went up by one, so both sides compute to the same thing and rfl closes it:

Most moves are like that: post restates apply in the terms a reader cares about, and the proof is rfl, a tuple of rfls, or a lemma about the model. When apply calls a function with real logic, prove a lemma about that function next to it and cite it, as Basics does for adding an item:

Checks you get for free

Presence: the control is there exactly when the move is enabled

A move's enabled says when it is available. Whether its control is actually on screen is a question about the view, so the app proves it. Counter's says Reset's control is in the view exactly when Reset is enabled:

The framework's layout and frame theorems carry that through to every frame the running app shows: the accessibility tree of the frame, for any text measurements and any window size.

Pressable: a click at its centre presses it

Being in the tree isn't enough: another node could be painted over the control, or it could be laid out with no size. Hit testing is Lean, so this is a theorem too. For a rigid view (chapter 3) the framework reduces it to a condition on the view alone, FitsIn, which Counter proves for any window at least 480 × 256:

The runtime's own theorems take it from there: if the pointer reaches a control at its centre, a pointer down and up there deliver exactly a press of that control to update.

Invariants

An invariant's proof is the most work in a typical app: init for the starting state, then one obligation per handler, each saying that handler keeps the property. The chapter on moves and flows shows the shape; the lemmas behind Basics' ^105 are about thirty lines of ordinary list reasoning in lean/Examples/Basics.lean.

The rules

These hold for every proof that counts as evidence, and make check enforces them:

  • No sorry. An unfinished proof fails the build.
  • Only the standard axioms: propext, Classical.choice and Quot.sound. The axiom audit looks at every theorem.
  • No escape hatches: native_decide, bv_decide, implemented_by, debug.skipKernelTC and axiom are rejected by a lint, and every declaration is replayed through the kernel.

For proofs about geometry, omega does most of the work, since layout is integers. For bounded enumerations, decide +kernel. For lists of nodes, write recursion structurally: children.map f makes a definition that rfl and decide can't see through.

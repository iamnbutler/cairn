The Cairn Book · Chapter 2

Moves and flows

Declaring what a person can do, the paths through it, and what must always hold.

Everything a person can do in a Cairn app is a move. A move is a claim: it has an id, a title, two sentences for people and a formal statement for Lean. The app's update is assembled from its moves and nothing else, so there is no behaviour without a claim. The framework proves that once, for every app: an action no move owns changes nothing and asks nothing of the host, and every effect an app asks for comes from an enabled move.

This chapter covers the claim kinds you write most: moves, flows and invariants. The claims reference has every clause.

A move

Here is Counter's Increment:

Reading it top to bottom:

  • move ^1 increment (s : State) "Increment" in ^3: the id, a Lean name, the state's name, the title, and the place the control appears in.
  • does and sees: what a person does and what follows. Reviewers read these, and the map is built from them. Both are required.
  • on press: one block per kind of action the move answers. The triggers are press, doublePress, submit, cancel, blur and edit, which also binds the text operation.
  • apply: the new state. Use emit instead when the move also asks the host to do something; it returns the new state and a list of effects.
  • post s': what must be true of the new state s', stated against the old one, s.
  • sound: the proof that apply meets post. A move without it doesn't compile.

With enabled, sound may assume it: the goal is "for every enabled state, post holds after apply", which is why its proof takes two arguments (intro s _).

Flows

A flow is a goal and a path that reaches it: a list of actions, each naming a move. Lean runs the path through the machine at compile time and checks two things: that every step is answered by an enabled move (so the path isn't a run of no-ops), and that the end state meets the goal.

A witness step names a control: press ^1, press ^103#1, edit ^101 (.insert "milk"), submit ^101. Basics adds a path with text and keys:

Flows are also what the map replays to take screenshots, and what the conformance driver replays against the running app.

Invariants

An invariant is a property that holds in every state the app can reach. You prove it holds at the start (init) and that every move keeps it (step). The commands then derive that it holds in every reachable state, and the runtime theorems carry that onto the screen. Basics' count of items left:

The step proof goes one move at a time: machine.preserves splits it, and each move's generated preserves lemma leaves one obligation per handler, stated over that handler's own apply. The lemmas it uses (add_inv, toggle_inv, delete_inv) are ordinary theorems in the same file. When the invariant is decidable, the command also makes it a runnable check, which the fuzzer runs after every step.

Places, assumptions and retired claims

Three more kinds complete the set:

  • A place is a region of the view where moves appear: a window, a menu, a panel.
  • An assumption (assume) is something the proofs rely on but can't prove, such as "the host reports clicks where they happen". It is recorded, never proved, and theorems that rely on it take it as a hypothesis, so every use shows.
  • A retired claim is a tombstone. Its id stays issued forever, with the reason it went.

Ids are the contract

An id is never renumbered or reused. claims.lock, at the root of the repository, records every id ever issued with a hash of its formal statement, and make check fails when an id disappears without being retired, comes back after it, or changes kind. When a claim's statement changes, the build warns: a new meaning needs a new id, or an explicit lake exe ledger update --accept that shows up in review.

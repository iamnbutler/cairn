Use

The evidence ladder

How sure we are of each claim: proved, fuzzed, tested, seen or assumed, computed by the build and shown on the map.

Every claim carries a list of evidence, one entry for each kind it can have. Each entry is a pass, a fail, or a gap: evidence the claim could have and doesn't, because the input wasn't run or never reached it. None of it is typed by hand; the build computes all of it.

The ladder

Strongest first:

KindWhere it comes fromPasses when
provedthe axiom audit of every theoremevery theorem the claim names (each handler's sound; a flow's live and reaches; an invariant's init, step and reachable) exists and uses only propext, Classical.choice and Quot.sound
fuzzedmake fuzz APP=<App>the claim's checks held in every random sequence that exercised it; for an assumption, every trusted-base check naming it held
testedmake conformance APP=<App>the running app matched the Lean model at every step that exercised it
seenthe map's capturea move's control is in a captured frame; a flow's whole witness was replayed, each step on the control it names
assumedthe claim is an assumealways: it is stated, never proved

Proved and fuzzed are about the Lean model; tested and seen are about the app. A proof says more, but only conformance reaches through the host, so a claim keeps every chip, not just its best one. A move is fully covered when it is proved, fuzzed, tested and seen.

Which kinds each claim can have:

Claimprovedfuzzedtestedseenassumed
move✓✓✓✓
flow✓✓✓
invariant✓✓✓
assume✓✓
place✓

Flows aren't fuzzed, because their paths are proved live. Invariants aren't seen, because a screenshot can't show that something holds in every state.

How a claim reads

To make a map scannable, each claim also reads as one word:

Reads asWhen
retiredit is retired: it shows its reason and nothing else
brokenany of its evidence failed
assumedit is an assumption, even when fuzzed
proved, fuzzed, tested or seenthe strongest kind it passes
untestedit is live and has no evidence at all

A fail is a named theorem missing from the audit or using another axiom; a fuzz failure, with the command that replays it; a conformance failure; or a flow whose step names a control the captured app doesn't show. A claim missing from claims.lock, or whose statement changed without being accepted, is reported with it.

The map

The map is the ladder as pages, one set per app: a summary of the evidence, the gaps (failures first), then a page per place with each move's does and sees, its evidence, its theorems, and before-and-after screenshots from the app's own frames, with pins on the controls. Each flow has a filmstrip of its replay. Claims are cited as page.html#N.

See the published maps.

What isn't evidence yet

  • Seen is the Lean model's own frames, rendered by the real renderer, not the running app's window. Conformance is what covers the host.
  • Some rarer text operations (word movement, input-method composition, cut and copy) aren't replayed by the capture yet, so a flow that uses one is only partly seen.
  • Presence and pressability theorems aren't linked to their claims yet, so they don't count toward a claim's proved. The fuzzer checks both for every move.
  • Kernel replay covers the whole build, not each theorem.
Cairn is research, and these docs grow with it. The code samples are included from the source that make check builds.

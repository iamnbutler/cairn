## Key findings (quoted)

**Cassius (2016).** "This paper presents the first mechanized formalization of a substantial
fragment of the CSS semantics … equipped with an efficient reduction to the theory of
quantifier-free linear real arithmetic" (abstract). Layout is a *relation*, not a function: "a
declarative browser … can perform the layout computation both forwards and backwards" (§2.1), so
one encoding gives a verifier, a debugger and a synthesizer. The verifier asks the solver for
layout parameters (viewport size) that break a property, e.g. `∀a,b. a.elt.tag = main ∧ b.parent
= a ⇒ contains(a, b)` (Fig. 3b).

- **Text is outside the model.** "Since Cassius does not model font metrics, the width and
  height of text boxes must be provided by tools that build upon Cassius, for example by
  rendering the text and measuring its size" (§3.1, footnote 5).
- **Conformance against a real engine.** Checked against all 2,075 relevant CSS 2.1 tests with
  Firefox as oracle: all accepted except six, where "The cause of the disagreement is rounding
  error within Firefox … Firefox represents on-screen lengths as fixed-point values rounded to a
  sixtieth of a pixel … Since Cassius uses real (infinite-precision) arithmetic … its
  specification does not admit this rounded value" (§5.1.1). Mutation test: of 20,750 mutants,
  152 accepted; "126 out of 152 were accepted because Cassius does not model font metrics … The
  remaining mutants (26 out of 152) are due to non-determinism in the CSS 2.1 algorithm for
  computing the shrink-to-fit width of floating boxes" (§5.1.2).
- **Escape hatch:** "an element can generate an opaque box, whose position is not related to any
  CSS properties or to any other boxes" (§3.3).

**VizAssert (2018).** "These guidelines must hold on the infinitely many possible renderings of
a web page generated by differing screen sizes, fonts, and other user preferences" (abstract).
Introduces *visual logic*: universally quantified formulas over boxes with linear arithmetic,
tree navigation (`parent`, `next`, `ancestor(cond)`) and colours (Fig. 3). Restrictions are
deliberate: "multiplications must involve a constant … only universally-quantified queries …
SMT solvers cannot reason about recursive properties, so visual logic provides the ancestor
function" (§3). The 14 guidelines (Table 1) include "Text is at least 14px tall", "Text can be
resized by up to 200%", "Text does not overlap", "Main button is big enough", and
`interactive_onscreen`. Evaluation: 62 pages × assertions = 502 checks, "414 successful
verifications, 64 true positives, 13 false positives, and 11 timeouts" for "screen widths
1024–1920 pixels, screen heights 800–1080 pixels, and default font sizes 16–32 pixels" (§5, Evaluation).

- **Counter-evidence (text boxes vs glyphs):** a false positive where "SALE" is reported as
  overlapping a date: "The text does not overlap … but the text boxes do because they reserve
  space for possible descenders … VizAssert thus detected a failure of the formal assertion,
  but not a failure of the accessibility guideline that the assertion formalized" (§5, discussion of Figure 9).
- **Interaction is out of scope:** Cornipickle "tests, for particular rendering parameters and
  sequence of user actions, temporal properties … since VizAssert does not reason about
  JavaScript, it omits Cornipickle's temporal operators" (related work).

**Troika (2019).** Whole-page SMT does not scale. "A modular layout proof splits a monolithic
verification problem into smaller verification problems, one for each component … Each
component specification can use rely/guarantee-style preconditions" (abstract). The key rule:
"well-formedness must be true layout-agnostically, as a matter of pure logic, independent of the
details of web page layout" (§3.1), i.e. `(⋀ P_c) ⇒ Q` is checked without the layout semantics.
Different components can be discharged by different tools ("a whole-page SMT-based verifier, a
new specialized verifier for component specifications, a model checker, and a random testing
tool", §1). Result: "a speed-up of 13–1469× over existing tools, taking verification time from
hours to seconds" (abstract). On coverage: "some features, such as table layout or flex box,
would involve significant effort to formalize … full formalization in the near future is
unlikely" (§2.2).

**Spineless Traversal (2025)** is about speed of incremental re-layout ("faster than the standard
approach on 83.0% of 2216 benchmarks, with a mean speedup of 1.80×", abstract). Correctness is by
differential testing: "the compiler can also generate a from-scratch layout" to compare against (§ on the layout compiler)
(§ implementation), and the authors "found compiler correctness challenging". Its related work:
Cassius-based verification exists but "none of these works investigate incremental" layout.

**μSkia (2026)** mechanizes a 2D rasterization semantics (Skia) **in Lean 4**: "the abstract
model, Layer terms, and μSkia commands, and their respective denotational / operational
semantics … under a thousand lines of code" (§ Lean Formalization). Numbers are idealised:
"Our Lean formalization instead uses an abstract model where points and colors are represented
by real numbers, which in practice means it is accurate *up to* anti-aliasing and rounding"
(§ Abstract Model). Optimizer output is "translation validated in Lean" (abstract).

## What the line of work does not do

None of it proves anything about a layout *algorithm* in a proof assistant. Cassius/VizAssert/
Troika trust an SMT encoding of a CSS fragment (validated by tests against Firefox) and Z3;
they verify *pages*, not engines, over *bounded parameter ranges*; they exclude text metrics,
JavaScript and interaction; flexbox and tables are unformalized. I found no mechanized proof of
a GUI layout algorithm (flexbox, stack, constraint) in Coq, Isabelle, Agda or Lean in a search
on 2026-10-23; see [../constraint-layout/README.md](../constraint-layout/README.md) for the
constraint-solver side, which is tested, not proved.

## For Cairn

- **Adopt (B):** VizAssert's stance that properties must hold "on the infinitely many possible
  renderings". Cairn's B theorems already quantify over window size and over
  `(m : TextMetrics) (hm : m.Valid)`. That is strictly stronger than VizAssert's bounded ranges;
  keep it, and state the minimum window size as an explicit hypothesis as GOAL.md does.
- **Adopt (B, D):** Cassius's split: text measurement is an input the layout model does not
  compute. Cairn already does this with `TextMetrics`. The VizAssert false positive is the
  warning: a theorem about *text boxes* (line height incl. descenders) is not a theorem about
  *ink*. Say so in `docs/trusted.md`, and make "pressable" talk about control boxes, never
  glyphs.
- **Adopt (B, C):** a small visual logic as the *statement language* for layout claims
  (`place` claims): ∀ boxes, linear integer constraints, tree navigation. Our "children inside
  parent's clip", "siblings disjoint", "control centre hit-tests to its move" are all
  expressible in it. Because our geometry is integers and our layout is a total Lean function,
  we prove them instead of SMT-searching them.
- **Adopt (B, C):** Troika's rely/guarantee shape for the B/C boundary. `LayoutFacts` is
  exactly a component specification, and the pressable theorem should be derived from layout
  facts "layout-agnostically" (pure logic over `Laid`), so C never unfolds `layout`. This also
  lets an app combine a proved container with an opaque one (Cassius's "opaque box") whose
  facts are assumed, listed in `docs/trusted.md`.
- **Adopt (B, F):** integer logical points instead of reals. Cassius's only disagreements with
  Firefox were rounding; μSkia proves things "up to anti-aliasing and rounding". Cairn's integer
  layout makes "no rounding in layout" true by construction; the remaining rounding is at the
  backing-scale multiply in the renderer, which belongs in `docs/trusted.md` and in the pixel
  probes (J).
- **Study (F, E):** μSkia is the nearest prior art for a *Lean* rendering semantics: layers,
  clip, blend over reals, with translation validation of optimized draw lists. If Cairn ever
  optimizes its frame's draw list (merging rects, dropping occluded draws), translation
  validation in Lean is the pattern, and μSkia's `Layer` terms are a template for "what the
  frame means". Note it depends on reals, so on Mathlib, which AGENTS.md rules out for now.
- **Study (J):** Cassius's conformance method: run the formal model in *acceptance* mode against
  the real engine's output on a test corpus, and in *rejection* mode against mutants. For J,
  that means: (1) the host's actual frame must be accepted by the model, and (2) mutate one
  coordinate and check the comparison catches it, so the comparison is known to be strong
  enough.
- **Avoid (B):** a constraint-solver or relational layout. Cassius needed non-determinism (line
  breaking, shrink-to-fit) and an SMT backend to be faithful to CSS; Cairn's layout is a
  function we write, so keep it deterministic and total.
- **Avoid (B):** incremental layout before we need it. Spineless Traversal shows how hard it is
  to get right ("we found compiler correctness challenging"); if Cairn adds it, prove
  `incremental = from-scratch` or at least test it differentially the way they did.

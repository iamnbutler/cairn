## Disselkoen et al., "How We Built Cedar: A Verification-Guided Approach", FSE Companion '24 (arXiv 2407.01688)

Why not ship Lean-compiled code (Section 1):

> One approach would be to develop Cedar entirely in Lean, compile to C, and deploy the generated
> C code in production. [...] But there are significant downsides to writing production
> applications in Lean and deploying its generated C code. Lean is a new programming language, so
> it has a limited developer pool and lacks useful libraries available in mainstream languages.
> Debugging a failure might necessitate stepping through the generated C code and mapping it back
> to the Lean source, requiring expertise in C and Lean. Doing so could be particularly difficult
> if the failure is due to an interaction between handwritten code and Lean-generated C code. In
> addition, C is a memory-unsafe language, so a bug in the Lean compiler could lead to security
> issues.

Why not verify Rust directly (Section 1):

> tools for verifying Rust code are not (yet) up to the task [...] teams would likely need to
> wrangle code into less idiomatic forms with each release just to enable proofs.

Model requirements (Section 3):

> First, the models should be human readable, and thus favor simplicity and understandability
> [...] Second, they should be as feature complete as possible, so that proofs about them apply
> to the production code [...] Third, [they] can be used as oracles for differential testing.

Sets and maps (Section 3.1):

> Lean requires all recursive definitions to be well-founded (so functions always terminate),
> which complicates modeling of complex recursive structures. While Rust lets us represent Cedar
> values as a recursive datatype over built-in sets and maps, Lean prohibits doing so for its
> standard set and map datatypes because their invariants introduce circular (not well-founded)
> reasoning. We worked around this by developing custom set and map datatypes that replace
> embedded invariants with separate theorems. Pleasantly, our termination proofs turned out to
> not be merely tedium: Constructing them helped us uncover and fix a non-termination bug in our
> definition of the Cedar validator, which would have been difficult to detect through testing.
> We also found three other bugs while attempting to carry out the validator soundness proof.

> our parsers are not modeled in Lean because there is currently no library support for parser
> generators [...] We also did not port our unit tests to Lean because we can instead prove
> properties of interest.

Section 3.2:

> This is the most involved proof we have done so far. [validator soundness]
> Our total proof-to-model ratio is roughly 3.4 : 1 (see Table 1).
> It takes about 3 minutes to check all proofs and compile models for execution. During
> differential testing, the median execution time for the Lean authorizer is 6 microseconds,
> compared to 10 microseconds for Rust.

(Note: one machine summary of the HTML version misread the ratio as "13.4:1"; the PDF says 3.4:1,
which matches 5714/1673.)

Section 4.3:

> We allocate 4096 CPU units (4 vCPUs) and 8GB memory to fuzz each target for 6 hours. This setup
> generates millions of inputs for most targets.

> Some bugs found by differential testing even affected Cedar's language design. For example, an
> unreleased early version of Cedar provided a method to get the size of a string. The model and
> production code ended up having different implementations (using bytes vs. codepoints vs.
> graphemes), causing DRT to fail. We eventually dropped this feature after agreeing that it
> confuses users more than it benefits them.

> All bugs found by the validation soundness property were found before we had completed a
> soundness proof.

> 35.5% of the when condition-expressions generated by the type-directed ABAC policy generator,
> for a typical DRT run, are boolean literals [...] For the expression generator, only 9.7% of
> Boolean-typed expressions are boolean literals.

> Limitations. Unsurprisingly, Cedar's testing framework has missed bugs, too. The most notable
> example is that it did not discover the non-termination bug described in Section 3.1. The
> reason for this is that the probability of generating inputs triggering this bug is extremely
> low. Our framework is also inherently unable to find bugs outside the scope of the test
> generators.

Table 3 (bugs found, selected): "The Rust implementation and definitional model computed string
sizes differently"; "The definitional model incorrectly rejected "::" when parsing IPv6
addresses"; six parser round-trip bugs ("The parser did not unescape raw strings", "Pretty-printing
did not consistently add parentheses to negation operations", ...).

Table 4 (bugs missed, selected): "The validator did not terminate on certain inputs | Triggering
input is too hard to generate"; "The parser crashed on certain malformed policies | DRT does not
methodically generate malformed policies".

## Hietala and Torlak, "Lean Into Verified Software Development", AWS Open Source Blog, 2024-04-08

> We adopted Lean to write our model because of its fast runtime, extensive libraries, and small
> trusted computing base.

> On average, Lean takes 5 microseconds to evaluate a differential testing input, compared to 7
> microseconds for Rust.

> It takes 185 seconds in total to check all proofs and compile models for execution. As a point
> of comparison, Rust takes 45 seconds to compile and test the implementation code.

> At 4,686 lines of code, this proof took 18 person-days to develop. [validator soundness]

> One challenge of using Lean is its strict termination checking. [...] its sparse documentation
> and sluggish termination checking for mutual induction.

Tips given: "Lean into the curve", "Start simple", "Stay flexible".

## Cedar RFC 0032, "Port Cedar formalization to Lean" (started 2023-10-12, accepted 2023-10-24)

> We chose Dafny for its balance of usability and ability to automatically prove basic security
> properties [...] proving Cedar's meta-theoretic properties (such as validator soundness) is less
> suited for Dafny's automation [...] For these proofs to be robust in terms of performance and
> maintenance, they need to be highly detailed, favoring the use of an interactive theorem prover.

## Shah, "A Lean Formalization of Cedar", POPL '24 SRC abstract (bhaktishh.github.io/papers/popl-24-src-abs.pdf)

> To define a quotient type representing sets on Value, we would need to define a function and a
> type in a mutually recursive fashion, something that is not permitted in Lean. Hence, we had to
> settle on an alternative definition: a set is a wrapper around a list, but we only deal with
> well-formed sets, that is, sets where the underlying list is sorted and duplicate free. Utility
> functions do not assume well-formedness, but we instead prove properties for each utility
> function that state that a well-formed input produces a well-formed output.

> as Dafny is able to discharge proof obligations to an SMT solver, just stating the lemma was
> enough for the language to succeed at verification. However, with Lean, all proofs needed some
> amount of manual intervention [...] Lean proofs were often longer than Dafny proofs, that could
> be empty.

| Element | Dafny LOC | Lean LOC |
|---|---:|---:|
| Generic datatype definitions | 0 | 738 |
| Language model specification | 1687 | 936 |
| Validation model specification | 1109 | 460 |
| Language model theorems & proofs | 394 | 354 |

> Averaged over 5 runs, we found Lean's average verification time to be 61.79s and Dafny's
> average verification time to be 115.12s

## cedar-spec repository (github.com/cedar-policy/cedar-spec, HEAD c9a0340, 2026-10-22)

`cedar-lean/GUIDE.md`, "Proof stability":

> To make version upgrades easier, strive to follow these guidelines:
> - Use `simp only` instead of `simp`. It's okay to use `simp` to close a goal.
> - Use `have` to deconstruct values. Use `rcases` only to split disjunctions.
> - Use `exact` instead of `apply` whenever possible.
> - Fully spell out types in function and theorem declarations.

`cedar-lean/Cedar/Data/Set.lean` module doc:

> This file defines a simple set data type, backed by a sorted duplicate-free list. Functions on
> sets assume but don't require their inputs to be well-formed (sorted and duplicate-free).
> Separate theorems show that these functions produce well-formed outputs when given well-formed
> inputs.

## SampCert (github.com/leanprover/SampCert; Tristan et al., arXiv 2412.01671)

`SampCert/SLang.lean`: the specification functions carry `@[extern]` C implementations:

```lean
@[extern "prob_Bind"]
def probBind (p : SLang T) (f : T → SLang U) : SLang U :=
  fun b => ∑' a, p a * f a b
...
@[extern "prob_While"]
def probWhile (cond : T → Bool) (body : T → SLang T) (init : T) : SLang T :=
  fun x => ⨆ (i : ℕ), (probWhileCut cond body i init x)
```

`SampCert.lean`:

```lean
-- The following is unsound and should NOT be part of the code
-- We are using it for now until the Python FFI is richer
@[extern "dirty_io_get"]
opaque DirtyIOGet(x : IO ℤ) : UInt32
```

Paper: SampCert uses "a small trusted codebase in order to compile SLang programs to conventional
languages like C++ and Python"; the Lean FFI route adds "only 57 lines of C++ to our trusted
computing base"; "SampCert is written in Lean with over 12,000 lines of proof."
